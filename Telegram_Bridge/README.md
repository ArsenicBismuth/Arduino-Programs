# Telegram Bridge

Small ESPHome program that does **one** thing: poll a Telegram bot, run the
matching HTTP request, and send back whatever text the target device produced.

It exists because `Smart_Door` used to poll Telegram and post status messages
itself, which competed with the servo control and web server for the ESP32's CPU
and memory — and needed the bot token. Now the door is Telegram-free: it only
exposes plain text over its REST API, and this device does all the talking.

```
Telegram  ──getUpdates──▶  telegram-bridge  ──POST──▶  http://smart-door.local/button/Status/press
          ◀──sendMessage──                  ◀──GET───  http://smart-door.local/text_sensor/Message
```

## Files

| File | Purpose |
| --- | --- |
| `telegram-bridge.yaml` | ESPHome configuration (this is the whole program) |
| `secrets.example.yaml` | Copy to `secrets.yaml` and fill in |
| `.gitignore` | Keeps `.esphome/` and `secrets.yaml` out of git |

## Setup

1. Copy `secrets.example.yaml` to `secrets.yaml` and fill in the WiFi, AP and
   Telegram values.
2. Install the ESPHome CLI: https://esphome.io/guides/getting-started-command-line.html
3. Flash it: `esphome run telegram-bridge.yaml`
4. Open http://telegram-bridge.local — the *Last Command* and *Last Result*
   sensors show what is happening, and *Reset Telegram Offset* re-syncs the
   bot cursor.

Getting the `telegram_chat_id`: message the bot once, then run
`python ../Smart_Door/macro/telegram.py --get-id` (it reads the token from the
bridge's `secrets.yaml`, falling back to `Smart_Door/secrets.yaml`). Use a
comma-separated list to allow more than one chat:
`telegram_chat_id: "123123123,456456789"`.

## The command map

All mappings live in `substitutions.command_map` at the top of
`telegram-bridge.yaml`:

```yaml
command_map: |-
  {"/open", "http://smart-door.local/button/Open/press", "http://smart-door.local/text_sensor/Message"},
  {"/close", "http://smart-door.local/button/Close/press"},
  {"/zero", "http://smart-door.local/button/Zero/press"},
  {"/status", "http://smart-door.local/button/Status/press", "http://smart-door.local/text_sensor/Message"}
```

Each entry is `{"/command", "http://host/path"}`. Every command is forwarded as
an **HTTP POST with an empty body**, so any ESPHome REST endpoint works
(`/button/<name>/press`, `/switch/<name>/turn_on`, `/select/<name>/set?option=...`
needs a body, so use a script endpoint or a query string instead).

The optional third value is a URL the bridge **GETs after the POST**. The
`value` field of that JSON response is sent to Telegram **verbatim** — that is
how the target device decides the message. An ESPHome text sensor works
directly: `GET /text_sensor/Message` returns
`{"id":"message","state":"...","value":"Status: Door is OPEN ..."}`.

So the text is not generated by the bridge at all; the bridge just relays it
(Markdown enabled, so the target may use `*bold*`). Without a third value the
bridge answers `OK: /command`.

Adding an action is one line — no other changes needed:

```yaml
command_map: |-
  {"/open", "http://smart-door.local/button/Open/press", "http://smart-door.local/text_sensor/Message"},
  {"/close", "http://smart-door.local/button/Close/press"},
  {"/zero", "http://smart-door.local/button/Zero/press"},
  {"/status", "http://smart-door.local/button/Status/press", "http://smart-door.local/text_sensor/Message"},
  {"/lights", "http://192.168.1.50/button/Desk_Lights/press"}
```

Notes:

- Command names are matched case-insensitively. `/open@MyBot` (group chat form)
  works too, and arguments are ignored (`/status now` → `/status`).
- `/help` (also `/commands`, `/start`) replies with an **inline keyboard**: one
  button per mapped command, two per row. Tapping a button runs that command;
  the result appears as a short toast on the button (`OK: /open`), so no extra
  chat message is added. The buttons always reflect `command_map`.
- A command without a text URL gets a short chat reply, `OK: /open` or
  `FAILED: /open`. The HTTP status code stays in the *Last Result* sensor and
  in the logs.
- Entity names in the URL are **case sensitive** and use the ESPHome entity
  `name:`, e.g. `name: Open` → `/button/Open/press`.
- `.local` names are resolved over mDNS. If a target does not answer, use its
  IP address instead (and give it a static DHCP lease).

## Behaviour

- **One request at a time.** Polling, forwarded commands and replies are
  serialised through a single `http_busy` flag, so the bridge never opens
  overlapping TLS connections.
- **Allowed chats only.** `telegram_chat_id` accepts one id or a
  comma-separated list (`"123123123,456456789"`). Messages and button presses
  from any other chat are ignored and logged. Replies and the `/help` menu go
  back to the chat that sent the command. Do not remove this check — the bot
  would otherwise be an open doorbell.
- **No replay after reboot.** The last handled `update_id` is persisted, so a
  reboot continues where it left off.
- **No replay after flashing.** On the first poll after a fresh flash the
  current cursor is stored and the backlog is dropped.
- **Stale commands are dropped.** Anything older than `max_command_age`
  seconds (default 120) is ignored, so a `/open` sent before an outage cannot
  fire hours later. Set it to `0` to accept any age. Button presses are exempt:
  the `/help` menu may legitimately be used much later.
- **Text relay.** When a map entry has a text URL, the bridge POSTs the action,
  then GETs that URL and sends the `value` field to the chat that asked. The
  target device is free to say anything; the bridge adds no wording.
- **Optional result replies.** With `send_replies: true` a command *without* a
  text URL answers `OK: /open` (or `FAILED: /open`). Set it to `false` to halve
  the number of requests. Relayed text is always sent.
- **Buttons always get feedback.** Telegram requires an `answerCallbackQuery`
  for every inline button press; that call doubles as the toast showing
  `OK: /status` / `FAILED: /open` without adding a chat message.

## Smart Door side

`Smart_Door` no longer mentions Telegram at all. It just exposes text over its
REST API, and this bridge relays it:

- `POST http://smart-door.local/button/Status/press` — puts the current status
  (door state, last opened/closed) into the `Message` text sensor.
- `POST http://smart-door.local/button/Open/press` — opens the door and puts
  `*Status: Door is OPENING...* 🟥` into the same sensor.
- `GET http://smart-door.local/text_sensor/Message` — returns the text.

The door needs no Telegram token, no chat id and no `http_request` component;
its `secrets.yaml` only holds WiFi credentials.

Mappings used by this bridge:

| Telegram | POST | Then GET |
| --- | --- | --- |
| `/open` | `/button/Open/press` | `/text_sensor/Message` (→ "OPENING...") |
| `/close` | `/button/Close/press` | – (replies `OK: /close`) |
| `/zero` | `/button/Zero/press` | – (replies `OK: /zero`) |
| `/status` | `/button/Status/press` | `/text_sensor/Message` (→ full status) |

## Tuning

| Substitution | Default | Meaning |
| --- | --- | --- |
| `poll_interval` | `1s` | How often `getUpdates` is called. `2s`–`5s` is easier on the ESP32. |
| `max_command_age` | `120` | Seconds before a command is considered stale (`0` = never). |
| `send_replies` | `true` | Answer commands without a text URL with `OK: /command`. |
| `request_timeout` | `8s` | Per-request timeout. |

Logs are available with `esphome logs telegram-bridge.yaml`.
